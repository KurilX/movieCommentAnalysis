## Problem Statement

作为一个要交论文、要答辩的毕业生，P0 让系统「能打开」了，但打开之后看到的数字**站不住脚**：

1. **L0 全是「还行」**。我在答辩上要讲「规则引擎 vs 深度学习 vs 大模型」三方案对比，可我的规则引擎只有 43 个情感词（正面 22 / 负面 15 / 中性 6），靠 `contains` 匹配。真实影评里「封神」「炸裂」「值回票价」「年度最佳」一个都不认识，于是 4000 条评论里 **62% 被判成中性**，Accuracy 只有 **37.4%**——比「无脑全猜正面」的 84.4% 差了整整一倍。老师只要问一句「你的基线怎么比瞎猜还低」，这一章就废了。

2. **换模型要等 3 分钟**。改完词典、想重跑全库看新数字，得点一次「一键重跑」，然后**盯着转圈等 3 分钟**（4000 条评论 × 7 次单条 insert = 28000 次 SQL 往返）。调参是多轮的事，等一次 3 分钟的反馈循环意味着我一天试不了几次。

3. **词云是假的词云**。详情页那个「关键词」区域本来是我论文里可视化章节的门面，现在输出的是 `the`、`12`、`然而痛心的是`——因为中文根本没做分词，只是把标点换成空格再按空格切。而且号称 TF-IDF，代码里其实只有 TF，IDF 那一半根本没实现。老师问「你的 IDF 在哪」，我拿不出来。

这三件事都不是「再加个功能」，是把已经交付的东西**从「能看」提到「能写进论文」**。

## Solution

三件独立的事，三条线并行推进：

1. **把规则引擎的词典从 43 词扩到 300-500 词**，并且从硬编码搬进 JSON 资源文件。词源两条腿走路：开放情感词库做底座（大连理工情感词汇本体库，带极性和强度），我拿 4000 条真实评论统计高频未覆盖词、由 AI 在开发期逐条读语境判定极性来补影视领域词（「封神」这类通用词库没有的）。同时顺手改两条判定规则。做完之后能拿出**三组 Accuracy 交论文**：旧词旧规则（37.4%）→ 新词旧规则 → 新词新规则，一眼看出「词典规模」和「规则设计」各自贡献了多少。及格线 85%（追平全猜正面），目标 90%。

2. **把一键重跑从 28000 次单条 insert 改成批量 insert**，3 分钟降到秒级。事务语义保持不变（要么全旧要么全新）。

3. **接 HanLP 分词，并把 TF-IDF 补成真的 TF-IDF**。默认走 portable 版（纯 Java 单 jar、词典内置、**完全离线**），保证演示路径不依赖网络；另外在后台数据管理页提供一个「下载完整版语言模型」按钮，下载到 gitignore 的本地目录，启动时检测到就自动用完整版。**但演示永远走 portable**。

做完之后，我能：改词典 → 秒级重跑 → 立刻看到新 Accuracy；打开详情页看到的是「剧情」「演技」「特效」这样的真词而不是长串噪声；论文里三方案对比表的第一行终于能看。

## User Stories

### 论文作者（我本人）

1. 作为一个论文作者，我想让 L0 规则引擎的 Accuracy 从 37.4% 提到至少 85%，以便基线对比不再是负贡献。
2. 作为一个论文作者，我想看到「旧词典旧规则 → 新词典旧规则 → 新词典新规则」三组数字，以便把提升归因到「词典规模」和「规则设计」两个因素上。
3. 作为一个论文作者，我想让词典维护在一个可读的 JSON 文件里而不是散落在 Java 代码的 `Set.of(...)`，以便在论文附录里直接引用词表。
4. 作为一个论文作者，我想让每个情感词带上极性（-1/0/1）、强度（1/2）和来源域（通用/影视），以便统计「影视领域词贡献度」并改进「情感词典的领域适配」这一节。
5. 作为一个论文作者，我想让词典扩充过程是可复现的（高频候选词统计脚本随仓库提交），以便答辩被问「你怎么选词的」时能现场跑一遍。
6. 作为一个论文作者，我想让中性词和情感词共现时以情感词为准（如「还行，但演技真好」判正面），以便修复「中性词一出现就压掉所有情感信号」这个明显错误。
7. 作为一个论文作者，我想让程度副词（非常/太/特别）在没有情感词时给出弱极性信号，以便减少「明显是夸但判中性」的误判。
8. 作为一个论文作者，我想在重跑全库时几秒内拿到结果，以便快速迭代词典和规则的参数。
9. 作为一个论文作者，我想让重跑过程保持单事务语义，以便中途失败时数据库不会停在半新半旧的状态。
10. 作为一个论文作者，我想在审计文档里记录批量改造前后的实测耗时，以便论文性能一节有真实数字可引用。
11. 作为一个论文作者，我想让关键词提取用真正的 TF-IDF，以便论文里「TF-IDF」这个词站得住脚。
12. 作为一个论文作者，我想让 IDF 在全部 4000 条评论上计算，以便「电影」「觉得」这类全站通用词被自然压低（而不是靠停用词表硬挡）。
13. 作为一个论文作者，我想让关键词先正确分词再统计，以便词云里出现的是「剧情」「演技」「特效」而不是「然而痛心的是」。
14. 作为一个论文作者，我想保留一份离线可用的分词方案（portable），以便答辩现场断网也能演示。
15. 作为一个论文作者，我想能手动下载完整版分词模型以获得更好的分词质量，以便线上环境和论文实验可以用更强的数据包。
16. 作为一个论文作者，我想让系统在没下载完整版时自动降级到 portable 且不报错，以便换机器部署时不因为缺文件而崩溃。

### 系统运维者（我自己，演示前）

17. 作为一个运维者，我想在后台数据管理页看到一个「下载完整版语言模型」按钮，以便不用手工 SSH 传文件。
18. 作为一个运维者，我想看得到下载进度或至少看得到「未下载 / 下载中 / 已就绪」的状态，以便知道能不能用完整版。

21. 作为一个运维者，我想在后台看到当前生效的分词器是 portable 还是完整版，以便演示前一眼确认状态。

### 影迷（最终用户）

22. 作为一个影迷，我想在电影详情页看到干净的、有意义的关键词标签，以便快速了解观众在讨论什么。
23. 作为一个影迷，我想让关键词里不再出现英文停用词和纯数字，以便词云不是一堆噪声。
24. 作为一个影迷，我想在提交自己的影评后得到更准确的情感判断，以便系统的反馈符合我的真实意图。

### 开发者（未来维护者）

25. 作为一个开发者，我想让词典加载器有明确的失败语义（文件缺失/格式错误时快速失败并说明原因），以便不在演示现场才发现词典没加载。
26. 作为一个开发者，我想让词典加载逻辑可被单独测试，以便验证「改了 JSON 之后引擎行为跟着变」。
27. 作为一个开发者，我想让批量插入的实现集中在持久层，以便分析业务逻辑不被 SQL 细节污染。

## Implementation Decisions

### 一、情感词典（L0）

**词源策略**：两条腿。

- **底座**：采用开放情感词库（首选大连理工情感词汇本体库，带极性/强度标注）。若该库因注册/下载限制不可得，**降级为纯统计方案**，不阻塞交付——此时词典规模以「4000 条评论的高频覆盖」为准，并在论文中如实说明词源。
- **领域增强**：从 `data/comments.csv` 的 4000 条评论中统计高频未覆盖表达（分词 + 频次过滤后取候选），由**开发期的 AI 逐条阅读语境**判定极性与强度，生成影视领域词。
- **不做人工筛选**：候选词的取舍由 AI 开发期判断完成，人只做最终 review（看 JSON diff）。
- **关键约束**：判断发生在**开发期**，产物是词典文件。**运行时仍是纯规则引擎，不调用任何大模型、不依赖网络**。

**存储形态**：独立 JSON 资源文件（放在后端资源目录），随构建打包。字段结构：

```json
[
  { "word": "封神", "polarity": 1, "strength": 2, "domain": "film" },
  { "word": "稀碎", "polarity": -1, "strength": 2, "domain": "film" },
  { "word": "还行", "polarity": 0, "strength": 1, "domain": "general" }
]
```

- `polarity`：`1` 正面 / `0` 中性 / `-1` 负面
- `strength`：`1` 普通 / `2` 强烈（对应开放词库的强度标注；旧词典里的词统一视为 1，明显的强表达标 2）
- `domain`：`general` / `film`，供论文统计领域词贡献

**加载器**：启动时一次性加载为内存索引（按词长降序，供最长匹配），加载失败（文件缺失/JSON 非法/词条缺字段）**快速失败并给出明确错误信息**，不允许静默降级成空词典——空词典会让全站变成「全判中性」，比崩溃更难发现。

**规模目标**：300-500 个词条（正面 + 负面 + 中性合计，含旧词典全部 43 词）。

**规则改动（两条，圈定范围）**：

- **a) 程度副词弱信号**：文本命中程度副词（非常/极其/特别/十分/相当/太/很）但没有任何情感词时，不再直接判中性，而是按副词方向给一个弱极性信号（具体方向与置信度由实现时确定，须在测试中固化行为）。
- **b) 中性词共现让位**：中性标记词（还行/一般/凑合/普通/中规中矩/过得去）不再无条件把结果拉向中性；当同一文本存在明确情感词时，以情感词判定的结果为准。
- **c) 否定窗口扩展、d) 平局默认倾向**：**本次不动**。

**验收线**：三组评测数字跑完，新词新规则的 Accuracy **≥ 0.85 为及格**，**≥ 0.90 为目标**。若卡在 85% 以下，回到词源继续迭代，不降低标准。

### 二、评测归因（三组数字）

统一用「真实星级」做金标准（4-5 星=正面、3 星=中性、1-2 星=负面），在 4000 条评论上跑：

| 组 | 词典 | 规则 | 用途 |
|---|---|---|---|
| ① 基线 | 43 词 | 旧 | 论文基线（已知 37.4%） |
| ② | 300-500 词 | 旧 | 隔离「词典规模」贡献 |
| ③ | 300-500 词 | 新（a+b） | 最终 L0 指标，验收线所在这组 |

三组的 Accuracy / macro-F1 / 混淆矩阵全部记录进审计文档与论文表格。②③ 由评测能力产出，评测语料直接复用现有 CSV 与星级映射逻辑，不新建标注集（标注集属 P2）。

### 三、批量插入（性能）

- 持久层新增**批量写入能力**：手写批量 insert 语句（一行 SQL 插入多行记录，单批上限 500 行），供文档级分析结果与方面级结果两条写入路径使用。**不引入新的 Service 层**、不用 `saveBatch`。
- 顺带在 JDBC 连接串启用 `rewriteBatchedStatements=true`。
- **事务语义不变**：重跑全库仍是**单个大事务**（首行即全表清空，必须保证「要么全旧要么全新」）。
- **不引入临时表/改名切换**：不做「双写切换」这类防读到空窗的设计，属过度设计。
- **验收方式**：**实测耗时前后对比即算赢**，不写性能自动化测试（CI 中不稳定、不值得）。前后数字写进 `docs/项目状态审计.md`。

### 四、分词与 TF-IDF（关键词）

**分词库选型**：HanLP **portable**（纯 Java 单 jar、核心词典内置、**完全离线**）作为**默认且演示路径唯一**的方案。

**完整版可选增强**：

- 后台**数据管理页**（仅 ADMIN 可见）新增「下载完整版语言模型」按钮，附带当前状态展示（未下载 / 下载中 / 已就绪 / 失败）与当前生效的分词器标识。
- 由**后端代理流式下载** HanLP 官方数据包到本地目录（如 `backend/hanlp-data/`），该目录**加入 gitignore**，不进 Git。
- **启动时检测**该目录是否存在有效数据集：存在则加载完整版，否则降级 portable。
- **下载失败/中断不影响主流程**：系统继续以 portable 运行，按钮可重试。
- 明确边界：**演示路径永远走 portable**，下载按钮是演示之外的可选增强。

**真 IDF**：

- 「文档」= 单条评论，「语料」= 全库 4000 条评论。
- 权重 = TF × IDF（IDF 用平滑形式，具体形式实现时确定并用测试固化）。
- 停用词表继续保留（挡住单字虚词），但通用高频词的抑制主要交给 IDF。

**作用范围**：分词只服务关键词提取路径。**L0 情感分析的匹配方式本次不改**（仍是 `contains` 最长匹配），这样「扩词」与「分词」两件事的评测结果才能各自归因（对应 Q9 的分两步：先扩词测一次，分词接入后再测一次，两个数字都进论文）。

### 五、测试接缝（零新增）

全部复用现有接缝，不引入新接缝：

| 接缝 | 覆盖 |
|---|---|
| `SentimentAnalyzer.analyze(text)` | 词典加载、规则 a/b 的所有行为测试（AGENTS.md 硬约束 1：全系统唯一 AI 测试接缝） |
| 评测能力（真实星级金标准） | 三组归因数字 |
| `KeywordExtractor.extract(texts, topN)` | 分词接入 + 真 IDF 的行为测试 |
| HTTP API 边界（MockMvc） | 重跑接口行为不变、下载按钮状态接口 |
| 「启动顺序」回归测试 | 词典加载器接入后，启动链仍保持 导入 → 预计算 → 播种 的顺序 |

### 六、接口契约变更

- 后台新增：完整版语言模型的状态查询与下载触发接口（路径由实现时按现有 `/api/admin/**` 约定命名，受 ADMIN 权限保护）。
- **现有接口响应契约不变**：`/api/movies/{id}/keywords` 仍返回 `{ keywords: [{ word, weight, count }] }`；雷达图仍用 `sampleCount`；`/api/admin/analysis/rerun-all` 仍返回 `{ message, count }`。
- **不改前端现有页面的既有字段读取**（本次新增的仅是后台数据管理页的按钮区块）。

## Testing Decisions

### 什么是好测试

只测**外部行为**，不测实现细节。给一条评论文本，断言 `SentimentAnalyzer.analyze()` 返回的极性与触发词；给一组文本，断言 `KeywordExtractor.extract()` 返回的词不含噪声；给一个 HTTP 请求，断言响应 JSON 的字段与状态码。**不测**内部用了哪个数据结构、不测 SQL 文本、不测 JSON 文件被读取的字节数、不测 Vue 渲染。

### 要测的行为

1. **词典加载**：加载后词条数为目标区间；极性/强度/域三个字段都能被正确读出；文件缺失或 JSON 非法时**快速失败**并给出可读错误。
2. **词典改动生效**：把某条评论文本里的旧词典命中词换成一个新词典里的影视领域词（如「封神」），断言极性判为正面——证明「加载的是文件而不是硬编码」。
3. **规则 a**：含程度副词但无情感词的文本，不再返回中性（行为按实现固化成断言）。
4. **规则 b**：中性标记词与情感词共现时，结果跟随情感词（正例：「还行，但演技真好」→ 正面；反例：仅「还行」→ 中性）。
5. **旧行为回归**：旧词典的 43 个词原有判定不变；局部否定（「不推荐，但是演技在线剧情紧凑」）结果不变；空文本仍抛 `IllegalArgumentException`。
6. **批量写入**：重跑后分析结果行数不增加（覆盖而非追加）、方面结果行数与六个维度一致；单事务语义在失败时回滚（可用约束冲突构造失败场景）。
7. **分词与关键词**：输出不含英文停用词（`the`/`and`）与纯数字；输出包含预期中文词（「剧情」「演技」）；`topN` 上限仍生效；空输入仍抛异常。
8. **真 IDF**：构造「A 词在全部文档出现、B 词只在少数文档出现」的语料，断言 B 的词权高于 A —— 这是 TF-IDF 的核心行为，也是当前实现做不到的。
9. **降级逻辑**：语言模型目录不存在时，分词器仍能正常工作（返回非空结果、不抛异常）。
10. **启动顺序**：词典加载/Schema/导入/预计算的顺序约束不被破坏（现有回归测试须继续通过）。

## Out of Scope

- **不做** L2 ONNX 模型导出（下一轮 P1，`ml/models` 仍不存在）
